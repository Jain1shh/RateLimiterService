Architecture

How It Works

Your app makes one HTTP call before processing any request. The rate limiter checks a Redis counter and responds instantly.

Client
Browser / App
request
Your App
Any API
POST /check
Rate Limiter
This Service
allowed/denied
Storage
Redis + MySQL
The rate limiter is completely stateless with respect to your business logic. It only knows: clientKey, req counts, and window size. Your app controls the limits per route.(default maxReq=10, resetInSeconds=60) You can use clientKey to implement any strategy you want — per IP, per user, or a global limit.

Endpoints

Check Rate Limit

POST /api/rate-limit/check Core endpoint

Query Parameters

Parameter Type Required Default Description
clientKey string required — Unique identifier. Use ip:route format.
maxReq int optional 10 Max requests allowed in the window.
resetInSeconds long optional 60 Window size in seconds.

Responses

200 Allowed
429 Denied 
{
  "allowed": true,
  "remainingRequests": 7,
  "resetInSeconds": 60

Integration Guide

Integrating Into Your App

Step 1 — Extract the client IP

java 
public String getClientIP(HttpServletRequest request) {
    String ip = request.getHeader("X-Forwarded-For");
    return (ip != null) ? ip : request.getRemoteAddr();
}

Step 2 — Call rate limiter before your logic

java 
@PostMapping("/{apiRoute}")
public ResponseEntity<?> {funcName}(HttpServletRequest request) {

    String clientKey = getClientIP(request) + request.getRequestURI();

    String url = "http://ratelimiter:8080/api/rate-limit/check"
               + "?clientKey=" + clientKey
               + "&maxReq=5&resetInSeconds=60";

    ResponseEntity<RateLimitResponse> check =
        restTemplate.postForEntity(url, null, RateLimitResponse.class);

    if (!check.getBody().isAllowed()) {
        return ResponseEntity.status(429).body("Too many requests.");
    }

    // your actual logic here
}
Per-Route Limits

Setting Different Limits Per Route

Each route gets its own independent Redis counter. Hitting /shorten doesn't affect the /stats counter.

POST /shorten
5 req
per 60 seconds — strict, creation is expensive
GET /stats/:code
30 req
per 60 seconds — relaxed, reading is cheap
POST /login
3 req
per 300 seconds — very strict, brute force protection
GET /public/*
100 req
per 60 seconds — open, public content
java — per route examples 
// Strict — link creation
"?clientKey=" + ip + ":/{URI}&maxReq=5&resetInSeconds=60"

// Relaxed — reading stats  
"?clientKey=" + ip + ":/{URI}&maxReq=30&resetInSeconds=60"

// Very strict — auth endpoints
"?clientKey=" + ip + ":/{URI}&maxReq=3&resetInSeconds=300"
Best Practices

Client Key Strategy

The clientKey is the Redis counter key. How you construct it determines the scope of the limit.

Strategy clientKey format Effect
IP only 192.168.1.1 One shared limit across all routes — not recommended
IP + Route ✅ 192.168.1.1:/URI Independent counter per route per IP — recommended
API Key + Route apikey_abc:/URI For authenticated apps with API keys
User ID + Route user_123:/URI For logged-in users — most precise
URL-encode the clientKey if it contains special characters like / when passing as a query param. Or replace / with - — e.g. 192.168.1.1-shorten.
